Lab guide 8

Remote Storage and Performance Monitoring

Mount someone else's disk over the network, and learn to read the numbers when storage is the bottleneck.

8-10 hours Both lab machines up and able to reach each other
Before you start
  • Run this lab with one machine as the NFS server and the other as the client — pick either pairing

1. Export an NFS share from the server

Package names and the export config differ slightly; the NFS protocol itself doesn't care.

Ubuntu / Debian — NFS server on Ubuntu
sudo apt install -y nfs-kernel-server
sudo mkdir -p /srv/nfs/lfcs-share
sudo chown nobody:nogroup /srv/nfs/lfcs-share
echo '/srv/nfs/lfcs-share  *(rw,sync,no_subtree_check)' | sudo tee -a /etc/exports
sudo exportfs -ra
sudo systemctl enable --now nfs-kernel-server
Rocky / RHEL — NFS server on Rocky
sudo dnf install -y nfs-utils
sudo mkdir -p /srv/nfs/lfcs-share
sudo chown nobody:nobody /srv/nfs/lfcs-share
echo '/srv/nfs/lfcs-share  *(rw,sync,no_subtree_check)' | sudo tee -a /etc/exports
sudo exportfs -ra
sudo systemctl enable --now nfs-server
sudo firewall-cmd --add-service=nfs --permanent && sudo firewall-cmd --reload

2. Mount it on the client, persistently

Once mounted, NFS behaves identically regardless of either machine's distro.

Ubuntu / Debian — NFS client tools on Ubuntu
sudo apt install -y nfs-common
sudo mkdir -p /mnt/lfcs-nfs
echo '<server-ip>:/srv/nfs/lfcs-share  /mnt/lfcs-nfs  nfs  defaults  0  0' | sudo tee -a /etc/fstab
sudo mount -a
df -h /mnt/lfcs-nfs
Rocky / RHEL — NFS client tools on Rocky
sudo dnf install -y nfs-utils
sudo mkdir -p /mnt/lfcs-nfs
echo '<server-ip>:/srv/nfs/lfcs-share  /mnt/lfcs-nfs  nfs  defaults  0  0' | sudo tee -a /etc/fstab
sudo mount -a
df -h /mnt/lfcs-nfs

3. autofs — mount on demand instead

Same package, same config file layout, on both distros.

Install autofs and configure an indirect map
sudo apt install -y autofs 2>/dev/null || sudo dnf install -y autofs
echo '/mnt/auto  /etc/auto.lfcs' | sudo tee -a /etc/auto.master
echo 'nfsshare  -fstype=nfs,rw  <server-ip>:/srv/nfs/lfcs-share' | sudo tee /etc/auto.lfcs
sudo systemctl enable --now autofs
ls /mnt/auto/nfsshare   # the access itself triggers the mount
mount | grep lfcs-share

4. Virtual filesystems

The exam names /proc and /sys specifically as things you should know how to read.

Read live kernel and hardware state through the virtual filesystems
cat /proc/cpuinfo | grep -c processor
cat /proc/meminfo | head -5
ls /sys/class/net/
cat /proc/version

5. Read storage performance output

iostat, vmstat, and du/df are how you prove where the bottleneck actually is.

Install sysstat if it's not already there, then read the numbers
sudo apt install -y sysstat 2>/dev/null || sudo dnf install -y sysstat
iostat -x 1 3
vmstat 1 3
df -h
du -sh /var/log/* 2>/dev/null | sort -rh | head -5

6. Find and reclaim space held by deleted-but-open files

df and du disagreeing is a classic symptom with one specific cause.

Reproduce it on purpose, then diagnose and fix it
sudo bash -c 'dd if=/dev/zero of=/tmp/bigfile bs=1M count=200 2>/dev/null; ( sleep 60; ) &' 
tail -f /tmp/bigfile > /dev/null &
TAIL_PID=$!
rm /tmp/bigfile
df -h /tmp
sudo lsof +L1 2>/dev/null | grep deleted | head -5
kill $TAIL_PID

Verify your work

Run these before you consider the lab finished.

  1. mount | grep lfcs-share # NFS mount present, either static or via autofs
  2. showmount -e localhost # export list correct, run on the server
  3. iostat -x 1 1 | tail -5
  4. df -h /tmp # space reclaimed after killing the process holding the deleted file
Break it, then fix it

Break:

sudo systemctl stop nfs-server 2>/dev/null; sudo systemctl stop nfs-kernel-server 2>/dev/null

What you'll see: The client's df -h on the NFS mount hangs or reports the share as unavailable. Any process cd'd into that mount may itself hang.

Fix:

# on the server:
sudo systemctl start nfs-server 2>/dev/null || sudo systemctl start nfs-kernel-server
# on the client, if it's still hung:
sudo umount -f /mnt/lfcs-nfs 2>/dev/null; sudo mount -a

Why it matters: An NFS server going away out from under a mounted client is one of the most realistic outages in this whole course — it happens by accident constantly in the real world, and the exam expects you to recognize the symptom instantly.
