Lab guide 6

Virtual Machines, Containers, and SELinux/AppArmor

The exam's virtualization and security objectives in one week — build a VM, run a container, fix a denial.

8-10 hours Week 5 complete. This week needs real console access — do it on the local hypervisor, not a cloud instance.
Before you start
  • Hardware virtualization support confirmed: egrep -c '(vmx|svm)' /proc/cpuinfo returns non-zero
  • If you're labbing inside a VM already, enable nested virtualization in your hypervisor first

1. Install a local hypervisor stack

libvirt/KVM is the same engine under the hood on both — the package names differ slightly.

Ubuntu / Debian — Install libvirt/KVM tooling
sudo apt install -y qemu-kvm libvirt-daemon-system virtinst bridge-utils
sudo systemctl enable --now libvirtd
virsh list --all
Rocky / RHEL — Install libvirt/KVM tooling
sudo dnf install -y qemu-kvm libvirt virt-install
sudo systemctl enable --now libvirtd
virsh list --all

2. Build and manage a VM from the command line

virsh and virt-install are identical regardless of host distro.

Create a minimal VM (adjust the ISO path to whatever you downloaded)
sudo virt-install \
  --name lfcs-test-vm --memory 1024 --vcpus 1 \
  --disk size=8 --cdrom /path/to/some.iso \
  --network network=default --graphics none --noautoconsole
Manage it once it exists
virsh list --all
virsh start lfcs-test-vm 2>/dev/null
virsh dominfo lfcs-test-vm
virsh shutdown lfcs-test-vm 2>/dev/null || true

3. Install and run a container engine

Docker needs its own repo; Podman ships in Rocky's default repos.

Ubuntu / Debian — Install Docker
curl -fsSL https://get.docker.com | sudo sh
sudo systemctl enable --now docker
sudo docker run --rm hello-world
Rocky / RHEL — Install Podman
sudo dnf install -y podman
podman run --rm hello-world

4. Build a minimal container image

A Containerfile and a Dockerfile are the same format — Podman reads Dockerfile syntax natively.

Write a two-line image and build it (adjust the run command to docker or podman)
mkdir ~/lfcs-container && cd ~/lfcs-container
cat > Dockerfile <<'EOF'
FROM alpine:latest
CMD ["echo", "built by lfcs lab"]
EOF
docker build -t lfcs-test . 2>/dev/null || podman build -t lfcs-test .
docker run --rm lfcs-test 2>/dev/null || podman run --rm lfcs-test

5. Rocky / RHEL — read and fix an SELinux denial

Never disable SELinux to make an error go away. Learn to read the denial instead.

Cause a real denial: serve a file from a non-standard, unlabeled location
sudo dnf install -y httpd
sudo systemctl enable --now httpd
mkdir -p /srv/lfcs-web
echo 'lfcs test page' | sudo tee /srv/lfcs-web/index.html
sudo sed -i 's#DocumentRoot.*#DocumentRoot "/srv/lfcs-web"#' /etc/httpd/conf/httpd.conf
sudo systemctl restart httpd
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/
Read the denial, then fix the context — not the setting
sudo ausearch -m avc -ts recent | tail -20
ls -Zd /srv/lfcs-web
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/lfcs-web(/.*)?"
sudo restorecon -Rv /srv/lfcs-web
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/

6. Ubuntu — read and manage an AppArmor profile

AppArmor profiles are path-based, not label-based, but the workflow is analogous.

Check status, then flip a profile between enforce and complain
sudo aa-status
sudo aa-complain /etc/apparmor.d/usr.sbin.tcpdump 2>/dev/null || echo 'install a package with a shipped profile to test, e.g. tcpdump'
sudo aa-enforce /etc/apparmor.d/usr.sbin.tcpdump 2>/dev/null
Read denials from the kernel log
sudo dmesg | grep -i apparmor | tail -10
sudo journalctl -k | grep -i apparmor | tail -10

Verify your work

Run these before you consider the lab finished.

  1. virsh list --all | grep lfcs-test-vm
  2. docker images 2>/dev/null | grep lfcs-test || podman images | grep lfcs-test
  3. curl -s -o /dev/null -w '%{http_code}\n' http://localhost/ # Rocky: expect 200, not 403
  4. sudo aa-status | head -3 # Ubuntu only
Break it, then fix it

Break:

sudo semanage fcontext -a -t default_t "/srv/lfcs-web(/.*)?"
sudo restorecon -Rv /srv/lfcs-web

What you'll see: The 200 becomes a 403 again — you just relabeled the content back to a context httpd isn't allowed to read.

Fix:

sudo semanage fcontext -a -t httpd_sys_content_t "/srv/lfcs-web(/.*)?"
sudo restorecon -Rv /srv/lfcs-web

Why it matters: This is the SELinux denial that traps the most candidates: the fix isn't a boolean toggle, it's putting the file context back to what the service is actually permitted to read. semanage + restorecon is the pattern, every time.
